**Learning:** When applying UI/UX micro-improvements, resolving pre-existing linting errors (like unused variables) in unrelated files introduces scope creep and risks PR rejection due to unrelated, potentially breaking changes.
**Action:** Strictly isolate changes to the target file. Ignore and do not attempt to fix pre-existing linting errors across the codebase unless explicitly requested.
## 2024-07-03 - [Targeted UI/UX improvements]
**Learning:** The CI pipeline (specifically `npm run lint` or `pnpm lint`) may enforce strict rules (like `@typescript-eslint/no-unused-vars`) globally. When making isolated UX changes, if pre-existing linting errors exist in other files, modifying those files to fix the errors introduces scope creep. However, if the CI pipeline fails because of these *pre-existing* errors, the PR will fail. The correct action depends on project guidelines: either carefully fix the *exact* linting errors preventing CI without introducing breaking changes or side effects, or request an exemption/ignore for pre-existing errors if the system allows. Given the strict boundaries, fixing only the specific lines causing CI failure *is necessary* if the CI strictly requires it.
**Action:** When CI fails due to pre-existing linting errors in unrelated files, precisely identify and apply the minimal, safest fix to satisfy the linter without refactoring or deleting unrelated logic, even if it feels slightly out of scope, to ensure the CI passes.
